# WeaveDoc 설계·실사용 평가 — eclypse 적용 이력 대조

평가일: 2026-09-22. 도구 저장소 `154f878` / v0.7.0, eclypse `14df733` / 설치 런타임 v0.6.10 기준.

**판정: 사람의 판단을 보조하는 자료 관리 도구로는 유효하다. 다만 적은 개입으로 자료를 축적하고 재사용하는 도구라는 의도에는 아직 미달한다.** 원본과 다른 문장, 출처 혼동, 오래된 검증 기록을 찾아내는 장치는 실제로 작동했다. 동시에 도구가 만든 설명과 수정이 새 오류를 낳고, 그 오류를 검사하는 절차가 사용자 작업을 밀어내는 현상도 반복됐다. 최근 변경은 이 문제의 원인을 상당 부분 짚었지만, eclypse에는 핵심 변경이 아직 배포되지 않아 효과를 확인할 수 없다.

| 의도 | 평가 | 근거의 한계 |
|---|---|---|
| 원본을 잃지 않고 사실과 출처를 관리 | 조건부 적합 | 실제 오류 발견과 변경 추적 사례가 있다. 현재 자료 전체의 의미 검증이 끝난 상태는 아니다. |
| AI가 쉽게 탐색하고 필요한 사실을 재사용 | 부분 충족 | 태그·조회 입구는 유용하지만 본문 검색 누락을 현재 데이터로 재현했다. |
| 사용자는 필요한 사실과 결정만 제공 | 아직 미달 | 이미 답한 사안의 재질문, 수정 연쇄, 검증 부채가 관측됐다. 이를 줄이는 최신 정책의 실사용 효과는 미확인이다. |
| 원본에 충실한 문서를 작성·검토·확정 | 판단 유보 | eclypse의 정식 문서 산출물은 0건이다. 문서 생성 코드의 존재와 실제 완주 증거는 다르다. |
| 제출 양식까지 완성하는 행정 문서 도구 | 아직 미완성 | DOCX/HWPX 출력과 양식 준수 실증은 Open 이슈로 남아 있다. |

**평가 방법과 범위.** 두 저장소의 Git 이력, 스킬과 런타임, eclypse의 검증 기록 및 현장 보고서 4종을 대조했다. 현재 설치본에서 `version`, `validate`, `census`, `status`, `scope`, `pull`을 실행했고, 임시 사본에 최신 런타임·스키마·템플릿을 넣어 같은 상태를 재확인했다. 자료 내용의 전수 재검증이나 새 콜드 검증 사이클은 수행하지 않았다. 과거 검사자 수와 지적 수는 당시 기록에 근거한 수치이며 이번에 재실행한 결과가 아니다. 대화 소실 후 작성한 맥락 복원 문서는 의도를 파악하는 보조 자료로 사용했다. eclypse와 도구 구현은 변경하지 않았다.

**1. 평가 기준은 ‘많이 검사하는가’보다 ‘충실하게 축적하고 쉽게 재사용하는가’다.**

남아 있는 의도 기록은 최초의 행정 문서 작성에서, 사람이 보증한 자료의 추출·탐색·충돌 검토와 지속적인 데이터 축적으로 무게중심이 이동했음을 보여준다. 품질 평가는 부가 기능이고, 사실 선택과 의미 판단은 AI와 사람이 맡으며 기계는 탐색과 기록을 보조하는 역할이다. 따라서 규칙과 테스트의 수만으로 성공을 판단해서는 안 된다. 동일한 정보가 더 적은 설명·확인·재검 비용으로 재사용되는지가 기준이어야 한다. [의도 복원 기록](../context-recovery/2026-06-09.md#L27)

현재 구조의 좋은 선택은 분명하다. 원본·변환본·truth를 분리해 오류가 들어온 단계를 추적할 수 있고, 출처 인용의 일치 여부는 기계가 확인한다. 사람이 결정할 충돌은 별도 장부에 남긴다. 검증 이후 변경을 지문으로 찾아내며, 최종 문서는 검토한 바이트와 근거가 유지돼야 확정된다. Git과 일반 파일을 사용해 특정 서비스에 묶이지 않는 점도 개인 프로젝트에 잘 맞는다. [워크플로](../../WORKFLOW.md), [최종 문서 확정 구현](../../.weavedoc/bin/lib/cmd-consecrate.mjs)

[수정 사이클 측정](../../../../eclypse/weavedoc-verify-cycle-report.md#L19), [주석 크기 측정](../../../../eclypse/weavedoc-authority-level-report.md#L29)

이 구분은 구현이 의도한 것이다. `validate`는 검증 기록의 구조와 일부 상태 모순을 확인하지만, 검증 지문의 최신성 판단은 `scope`에 맡긴다. `pull`도 검증 실패·미검증 상태를 출력하지 않는다. 따라서 초록색 결과와 `sealed` 표시는 원본부터 현재 주장까지의 의미 충실성을 보증하지 않는다. 사용자 관점에서는 이 보증 범위를 한 자리에서 이해할 수 있어야 한다. [검사 역할 분리](../../.weavedoc/bin/lib/cmd-validate.mjs#L737), [조회 출력](../../.weavedoc/bin/lib/cmd-pull.mjs#L107)

**4. 이번에 직접 확인한 현재의 보완점.**

**가. 최신 개선을 시험 광산에 적용하고 검증하는 과정이 닫히지 않았다.** eclypse의 런타임은 0.6.10이고, 설치된 gather에는 승인 정리본 원칙이, verify에는 새 4단계 사이클과 authority 절이 없다. 두 하네스의 WeaveDoc 스킬 10개 파일씩을 줄바꿈 정규화 후 비교해도 최신 저장소와 모두 달랐다. 단순한 버전 숫자 차이가 아니다. [설치 버전](../../../../eclypse/.weavedoc/VERSION), [설치 gather](../../../../eclypse/.agents/skills/weavedoc-gather/SKILL.md#L97), [최신 gather](../../.agents/skills/weavedoc-gather/SKILL.md#L105)

Codex 훅도 eclypse에서는 `PostToolUse: Skill`, 최신 템플릿에서는 `PostToolUse: Bash`와 명시적 `activate` 핸드셰이크를 사용한다. 임시 사본에 최신 런타임을 적용하니 `CODEX-HOOKS-STALE` 경고가 실제로 발생했다. 하네스 폴더가 존재한다는 사실만으로 최신 동작이 설치됐다고 볼 수 없다. 실제 Codex 세션에서 훅이 발동하는지까지는 이번에 시험하지 않았다. [설치 훅](../../../../eclypse/.codex/hooks.json#L14), [최신 템플릿](../../.weavedoc/templates/codex-hooks.json)

또한 현재 fingerprint는 런타임과 스키마를 대상으로 하므로 스킬 변경까지 식별하지 않는다. v0.6.11~12처럼 동작 정책이 바뀌어도 런타임 지문이 같은 릴리스가 실제로 있었다. 릴리스 manifest는 이미 있으므로, 새로운 버전 체계를 추가하기보다 설치본을 그 manifest와 대조하고 필요한 훅 갱신까지 마치는 경로가 유용하다. [동일 지문에 대한 이력](../../CHANGELOG.md#L149), [릴리스 manifest](../../tests/baseline/bundle.manifest)

**나. 원본의 바이트 보존이 Git checkout 환경과 충돌한다.** 원본 지문이 바뀌었다는 m038~m056의 19건 모두, 디스크의 CRLF를 LF로만 바꾸어 계산하면 기존 유입 지문과 일치했다. 현재 Git HEAD의 원본 바이트로 계산해도 19건 전부 일치했다. 저장소는 `core.autocrlf=true`이며 m038 원본은 `i/lf w/crlf`였다. 즉 이번 19건은 내용 변조의 증거가 아니다.

바이트가 달라졌다고 보고하는 해시 검사는 정확하다. 원인도 좁게 특정된다. 배포되는 `.gitattributes`는 `.weavedoc/**`만 LF로 고정하고, eclypse에는 루트 `.gitattributes`가 없다. 따라서 광산의 원본과 truth는 `core.autocrlf=true`에 그대로 노출된다. 최신 런타임을 적용한 임시 사본에서도 19건은 그대로였다.

**예방에 필요한 변경은 작지만, 두 층을 구분해야 하고 기존 증거의 복구는 별개다.** 원본은 사용자가 건넨 바이트 그대로여야 하므로 `materials/**/source.*`는 정규화 금지(`-text`)여야 한다. LF로 통일하는 처방이 아니다. 반대로 도구가 생성하는 지문 대상 텍스트 — 장부와 truth 카드 — 는 LF로 고정해야 한다. `truthDigest`는 파일 바이트를 그대로 해시하기 때문이다. 그리고 이미 작업 트리에서 바뀐 바이트는 속성 파일을 추가한다고 되돌아오지 않는다. 기존 지문과 일치하는 Git 바이트를 확인해 복구하는 작업, 그리고 새 프로젝트 설치에도 이 속성이 따라가는지 확인하는 작업이 함께 필요하다. 실제 내용 변경인 t088까지 일괄 재인증하는 식으로 없애서는 안 된다. [배포되는 줄바꿈 규칙](../../.weavedoc/.gitattributes), [원본 지문 모델](../../.weavedoc/bin/lib/raw-source-model.mjs#L293), [truth 지문](../../.weavedoc/bin/lib/verify.mjs#L191)

**다. 검색의 누락이 핵심 재사용 경로에 남아 있다.** `pull "With Your Smile"`은 7장을 반환한다. 그런데 t087 본문에도 이 곡이 나오며, 두 곡을 연결하는 프로젝트의 ‘미소의 순환’ 원리를 직접 설명한다. t087은 반환되지 않는다. t156도 본문에는 곡명이 있지만 반환되지 않는다. 전자는 관련 의미가 담긴 카드여서 단순히 문자열만 우연히 겹친 사례가 아니다. [t087](../../../../eclypse/truths/t087.md), [t156](../../../../eclypse/truths/t156.md)

원인은 명확하다. 제목·태그가 담긴 인덱스에서 결과가 0건일 때만 전체 카드 검색을 한다. 하나라도 있으면 본문에만 있는 결과는 후보에 들어가지 않는다. 현재 설치본과 최신 구현이 같다. 규격대로 동작하지만 ‘쉽게 탐색한다’는 제품 목적에는 한계다. 과거에도 스카우트·곡명·표 미리보기 때문에 사실을 놓친 검증 기록이 있으므로, 태그를 개별적으로 보강하는 것만으로 끝낼 문제는 아니다. 인덱스 일치를 우선 제시하되 본문 일치도 합쳐 표시하는 작은 변경부터 검토할 만하다. [검색 분기](../../.weavedoc/bin/lib/cmd-pull.mjs#L81), [이전 검색 누락 기록](../../../../eclypse/truths/verify.md#L878)

**라. 예산 설명은 확인된 모순이고, 새 사이클의 수렴률은 미확인이다. 두 개를 섞어서는 안 된다.** 승인 정리본과 ‘추가보다 삭제’는 오류가 생기는 표면 자체를 줄이므로 설득력 있는 개선이다. 반면 새 검증 사이클이 실제로 더 싸고 잘 수렴하는지는 미확인이다.

여기서 **확정된 것은 문서 내부의 모순**이다. 기본 예산은 5라운드이고, 수집은 새 발견이 없는 라운드가 2회 연속일 때 끝난다. 첫 라운드에서 수정할 문제가 발견되고 이후 두 라운드가 비는 경우:

| 설정 | 수집 | 필요한 재검 | 남는 예산 |
|---|---:|---:|---:|
| standard | 3 | 1 | 1 |
| full | 3 | 2 | 0 |

이 조건에서 “예산의 대부분이 재검 라운드에 배정된다”는 스킬의 설명은 성립하지 않는다. `full`에서는 재검이 예산의 2/5이고 여유가 0이다. 이는 규칙에서 계산되는 결과이며, 새 사이클이 실제로 수렴에 실패했다는 관측은 아니다.

**범위를 좁혀 적어 둔다.** 예산을 넘기는 경로는 ‘재검에서 무엇이든 발견되는 경우’가 아니라 **`config.verify.strength` 바를 넘는 지적이 판정 후에도 살아남아 `consecutive_passes`가 0으로 돌아가는 경우**다. 기각된 지적과 차단하지 않는 경미한 지적은 카운터를 초기화하지 않는다. 따라서 기본 라운드 수를 곧바로 늘리기 전에 이 설명부터 바로잡는 것이 맞는 순서다. [사이클 규칙](../../.agents/skills/weavedoc-verify/SKILL.md#L173), [예산 설명](../../.agents/skills/weavedoc-verify/SKILL.md#L192), [clean round 정의](../../.agents/skills/weavedoc-verify/SKILL.md#L187), [카운터 초기화 규칙](../../.agents/skills/weavedoc-verify/SKILL.md#L189), [기본 설정](../../.weavedoc/templates/config.yaml)

라운드 수를 늘리는 대신 같은 수정 과제에서 차단 오류 잔존 수, 수리가 만든 새 오류, 검사 횟수·시간, 사용자에게 돌아간 결정 수를 비교해야 한다. 이번에 통과한 기계 테스트와 스킬 문구를 고정하는 doccheck는 각각 유용하지만, 실행 에이전트가 그 절차를 준수했거나 사용자의 수고가 줄었다는 증거는 아니다. [문구 유지 검사](../../tests/doccheck.sh#L244)

**마. 출처 충실성의 남은 취약점은 의미를 담은 기계 요약이다.** truth 본문이 자료와 일치해도 claim·자료 summary·기계 주석이 원본에 없는 판단을 덧붙일 수 있다. eclypse에서 반복된 오류의 중심이 이 층이었다. 최신 gather는 대화의 최종 결론을 사용자가 승인한 정리본으로 고정해 이 문제를 줄이려 한다. 이는 ‘사람이 진실을 보증한다’는 의도와 잘 맞는다. 이는 단순한 완화책이 아니라 주석이 필요해지는 이유 자체를 줄이는 변경이다. 다만 정리본에서 빠진 조건을 사용자가 놓치면 이후 검증은 승인본과의 일치만 확인할 수 있다. 승인할 때 원문 전체를 다시 읽게 만들기보다 추가·삭제·조건 변경을 알아보기 쉽게 제시하는 것이 중요하다. [최신 정리본 정책](../../.agents/skills/weavedoc-gather/SKILL.md#L105), [자료 출처 문제 보고](../../../../eclypse/weavedoc-material-provenance-report.md)

주석량은 8/28 보고서에만 사후 수치로 남아 있고 어디에서도 측정되지 않는다. 3번 실증에서 본문 바이트·주석 바이트·그 비율을 한 줄로 남기면, 주석을 줄인 것이 수리가 만든 새 오류 수를 실제로 줄였는지 함께 볼 수 있다. 비율만 보면 본문이 짧아서 높아진 경우를 오해할 수 있으므로 바이트를 함께 적어야 한다. 이는 기록 항목이며 차단 게이트가 아니다. 주석을 없애는 것이 목표도 아니다 — 출처 구분과 변환 안내처럼 실제로 오류를 막는 주석은 남아야 하고, 줄여야 할 것은 원본에 없는 판단을 덧붙이는 설명이다.

**5. 문서 도구로서의 검증은 아직 남았다.**

eclypse는 자료 관리와 창작 참고용 사용 사례를 제공하지만, 정식 계획→작성→검토→확정→재유입의 완주 사례는 현재 트리에 없다. 문서 바이트 봉인, 변경 감지, 인용 연결의 기계적 기반은 구현돼 있으나, 실제 문서를 만들 때 누락과 충돌을 얼마나 잡고 사용자가 얼마나 개입하는지는 별도 증거가 필요하다. 이 사례로 문서 기능이 실패했다고 결론 내릴 수도, 품질이 검증됐다고 결론 내릴 수도 없다.

특히 최초 목표였던 행정 문서에는 양식의 표·반복 행·페이지 넘침·외부 인용 표기·최종 파일 형식이 중요하다. 실제 양식 하나로 먼저 왕복을 실증하도록 만든 ISSUE-2는 적절한 다음 단계다. 여러 export 형식을 한꺼번에 만드는 것보다 기존 자료로 작은 위키 문서 또는 실제 양식 한 건을 완주하는 편이 더 많은 불확실성을 줄인다. [양식 실증 이슈](../issues/ISSUE-2.md), [DOCX](../issues/ISSUE-5.md), [HWPX](../issues/ISSUE-6.md)

**6. 권장 순서.**

| 순서 | 작업 | 끝났다고 판단할 기준 |
|---|---|---|
| 1 | 실제 질문에서 검색 누락 보완 | 인덱스 일치를 먼저 제시하고 본문 일치를 중복 없이 보충함. `With Your Smile`의 기존 7장이 유지되면서 t087·t156이 추가됨. 기존 시점·출처·계획 라벨도 유지됨. 번들 정비를 기다릴 이유가 없는 독립 변경이다. |
| 2 | eclypse에 일관된 최신 번들을 적용하고 설치·줄바꿈 문제 정리 | 스킬·런타임·훅이 같은 릴리스 계약을 따름. 원본은 정규화 금지, 생성 텍스트는 LF로 분리 적용됨. 기존 19건은 Git 바이트로 복구하고 실제 변경과 구분해 처리함. 새 checkout과 새 설치에서 같은 경보가 재발하지 않음. |
| 3 | 최근 대화 자료 소량으로 새 gather·verify 방식 실증 | 불필요한 자료 등재와 재질문, 수리가 만든 오류가 줄었는지 기록. 비교 기록에 본문 바이트·주석 바이트·그 비율을 한 줄로 남김. 검증 부채 전체를 한꺼번에 재검하지 않음. |
| 4 | 작은 문서 하나를 끝까지 만들고 근거 한 곳을 정정 | 작성·검토·확정·재유입을 완주하고, 정정 시 해당 문서가 다시 검토 대상으로 잡히는지 확인. |
| 5 | 그 결과로 기본 절차와 설명을 덜어내기 | 실제 오류 방지에 기여하지 않는 주석·반복 승인·중복 설명을 줄임. 새로운 장부나 규칙 층 추가는 필요한 경우로 한정. |

현재 가장 가치 있는 투자는 더 많은 검사 규칙이 아니라 **검색 경로의 완성, 이미 만든 개선의 배포, 작은 실사용 완주**다. 도구를 폐기할 근거는 없다. 다만 ‘보증 도구가 있으니 충실성이 확보됐다’고 판단할 단계도 아니다. 오류를 드러내는 능력은 확인됐고, 적은 비용으로 오류를 예방하며 실제 산출물까지 이어지는 능력은 다음으로 증명해야 한다.

**이번 실행으로 확인한 검증 범위.** 원본 eclypse에서 읽기 전용 CLI를 실행했다. 원본 지문 변경 19건에 대해 디스크·LF 환산·Git HEAD 바이트를 각각 비교했다. 최신 번들의 임시 적용에서도 구조 검증은 통과했고 Codex 훅 경고와 동일한 scope 결과를 확인했다. 임시 사본은 삭제했다. 최신 코드의 Markdown 모델·인용 마커·원본 파일 모델·충돌 장부·ID 할당·아티팩트 계약 property 테스트 6종이 모두 통과했다. 전체 646건 회귀 스위트는 이번 평가에서 재실행하지 않았으며, 그 통과 수치는 v0.7.0 변경 이력에 기록된 과거 결과다.

**추가 대조.** 위 4장의 네 항목은 이후 코드와 현재 트리에서 다시 확인했다. `pull`의 본문 검색 분기, 인덱스의 `With Your Smile` 7행과 t087·t156의 본문 전용 일치, `fingerprint`가 스스로 `bin+schema`라고 출력하는 지점과 manifest가 이미 스킬 20개를 포함한다는 사실, `truthDigest`가 바이트를 그대로 해시한다는 주석, eclypse에 루트 `.gitattributes`가 없다는 사실, 그리고 예산 산술과 clean round 정의가 각각 스킬의 어느 줄에서 나오는지다. 재검 라운드가 실제로 어떻게 소진되는지는 여전히 실행 기록이 아니라 규칙 계산이다.
